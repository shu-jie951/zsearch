# ZSEARCH 功能剖析

> 分析对象：`E:\网盘\zsearch`（本地项目，Vue 前端 + Express 后端）
> 分析方式：读源码（不做内存级逆向），关键路径标注 `文件:行号`
> 时间：2026-10-19 · 运行时探测见第 8 节

---

## 0. 一句话结论

**它自己没有任何网盘资源，也不建索引。** 它的全部能力是：把同一个关键词同时甩给 4 个第三方搜索源，把各家格式迥异的返回（JSON / SSR HTML）解析成统一结构，然后去重、打分、排序、折叠，最后把用户点的那一条，经过域名白名单校验后 302 跳过去。

技术上是「聚合器 + 转发器」，业务上是「盗版分享链接的索引页」。

---

## 1. 「获取资源」这件事的三层真相

### 1.1 第一层：不自建索引，全部实时查询

`lib/sources/index.js` 只注册了 4 个适配器，没有一个本地数据库或爬虫。每次用户搜索，`aggregator.search()` 用 `Promise.allSettled` 并发扇出（`lib/aggregator.js:282`），谁先回来用谁。

磁盘上唯一的数据是 `data/` 里的演示兜底数据，`lib/fallback.js` 明确标注 `_fallback: true`，落地页指向 `/unavailable`，不让用户点到假链接。

### 1.2 第二层：上游的索引是怎么来的

这是用户真正问的问题。上游分两类，来源完全不同：

| 类型 | 代表 | 索引怎么来的 |
|---|---|---|
| **众包/爬虫型** | PanSou、混沌搜 | 长期监听上百个 Telegram 分享频道 + 各类插件，把频道里贴出来的分享链接抓下来落库、建倒排 |
| **站长自建型** | zreso（原站）、j-so（旧版） | 站长自己维护的资源库，服务端渲染成页面或 JSON 接口 |

关键点：**网盘分享链接本身是"知道链接就能打开"的公开链接**，上游并没有破解网盘，也没有破解加密分享（带提取码的也没解）。它只是把散落在 TG 频道、论坛、贴吧里的链接收集起来，做成可搜索的表。所以从技术上说，这里没有任何"绕过加密"的动作；从法律上说，它仍然是侵权内容的索引与扩散。

### 1.3 第三层：本站做的四件事

1. **归一化**：把 4 种完全不同的字段结构压成同一个 shape（`title/date/cloud_type/status/raw_url/provider`）
2. **去重**：`dedupeKey()` 把链接归一到 `host+path`（去掉 `www.`、尾斜杠、全部 query 参数 —— 因为夸克/UC 的 query 基本都是跟踪参数），`lib/aggregator.js:65`
3. **打分排序**：质量分 + 相关性 + 日期新鲜度三路融合
4. **跳转管控**：真实链接**永远不下发给前端**，只给 `/go/<hash>` 短链

## 2. 四个数据源：四种完全不同的取数机制

| 源 | 站点 | 协议 | 拿到的是直链吗 | 特征 |
|---|---|---|---|---|
| `pansou` 盘搜聚合 | so.252035.xyz | POST `/api/search` JSON | 是 | 字段最全，带 TG 频道来源与提取码 |
| `hunhepan` 混沌搜 | hunhepan.com | POST `/open/search/disk` JSON | 是 | 带 tags + 文件清单，质量最高 |
| `jso` 珈珈搜索 | j-so.com | GET SSR **HTML** | 是 | 无 API，靠正则从 HTML 抠 |
| `zreso` 原站索引 | zreso.cn | GET `/api/search` JSON | **否**（中转链） | 有 Turnstile 风控，最脆 |

### 2.1 pansou（`lib/sources/pansou.js`）

- 入参是 `kw` 不是 `q`，`GET` 会 400，必须 `POST`
- 请求体：`{ kw, res: 'merge', cloud_types?: [key] }`
- 返回按网盘类型分组在 `data.merged_by_type` 下，逐组展开
- 每条带 `source`（如 `tg:xxx` / `plugin:xxx`）—— **这一条直接暴露了它的索引来自 Telegram 频道**
- 20s 超时（比其他源长，因为它确实慢）；400/429 触发指数退避 30s × level，封顶 5min

### 2.2 hunhepan（`lib/sources/hunhepan.js`）

- 请求体只吃 `{q, page, size}`，多传任何字段直接「参数错误」
- **`size` 无效，每页固定 10 条** → 并发翻 3 页凑 30 条（`fetchPage` 用 `list.length >= 10` 判断还有没有下一页，不能用过滤后条数判断，否则会少拉）
- `code=417` = 没有结果，**按软空处理而不是错误**
- 必须带 `Referer` + `Origin`，否则被拦
- `disk_name` / `files` 里关键词被 `<em>` 包裹，入库前要 `stripTags`
- `files` 是 `\n` 分隔的文件清单，取前 3 行当描述 —— 比标题信息量大得多

### 2.3 jso（`lib/sources/jso.js`）

这个源的机制最特别，也是**目前已经失效**的那个：

- 没有 JSON API，是**服务端渲染的 HTML**
- 路径 `/s/<urlencode(关键词)>`
- **默认只吐骨架屏**，必须同时满足两个条件才拿到完整结果：
  - URL 带 `?__full=1`
  - 请求头带 `X-Search-Full: 1`
- 真实直链直接内嵌在 `data-real-link="https://pan.quark.cn/s/xxx"` 属性里，所以不需要二次解析
- 另有一个 `/api/check_cloud.php?url=<链接>&t=<unix秒>`，用来标「有效/失效」—— `t` 缺参会返回「请求已过期」
- 解析用 5 条正则（`<article class="result-item">` / `data-real-link` / `<h2 class="result-title">` / `meta-item` / `result-status`），结构一改版就全空

### 2.4 zreso（`lib/sources/zreso.js` + `lib/upstream.js`）

- 唯一一个返回**中转链接**的源：`first_url` 是 `/api/wash?t=<uuid>`
- 要拿真实地址得再请求一次 wash 接口，返回 JSON 里的 `raw_url`
- 风控：被识别时 `429` + `{"error":"TURNSTILE_REQUIRED"}`，返回 HTML 也视同被拦（`lib/upstream.js:112-117`）
- 它单独有整套缓存/限速/熔断层（`lib/upstream.js`），其他三个源没有

## 3. 一次搜索的完整数据流

```
用户输入关键词
  │
  ├─ ① 聚合缓存命中？(3min TTL) ──是──▶ 直接返回
  │
  ├─ ② 并发扇出 4 个源（每个源自带 5min 缓存 + 自己的退避）
  │     pansou / jso / hunhepan / zreso
  │     单源异常 → 返回 [] ，绝不抛错拖垮整体
  │
  ├─ ③ 单源截断 maxPerSource = 120（防止一个源用几百条把别的源挤没）
  │
  ├─ ④ 统一清洗：title/note 过 cleanTitle()，去掉尾部的网盘名、emoji、半个括号
  │
  ├─ ⑤ 去重入桶：key = host + path（去 www / 去尾斜杠 / 丢 query）
  │     同一 key 命中多次 → mergeInto() 按质量分择优，并记录 _providers
  │
  ├─ ⑥ 网盘类型过滤（cloud != all 时）
  │
  ├─ ⑦ 相关性打分 relevance() → 排序 finalRank = rel×3 + 日期加成 + 质量分×0.25
  │
  ├─ ⑧ 同标题折叠（标题 ≥4 字且含 ≥4 个实义字符才折，防止把「资料」这种泛称误并）
  │
  ├─ ⑨ 总上限 300 条 → 每条生成 /go/<hash> → 安全标注 → 字段白名单下发
  │
  └─ 全部源都没结果 → buildFallback() 本地演示数据 + suggest 变体建议
```

关键参数（`config.js`）：

| 参数 | 值 | 作用 |
|---|---|---|
| `perSourceTimeoutMs` | 9000 | 单源兜底超时 |
| `maxPerSource` | 120 | 单源截断 |
| `maxTotal` | 300 | 总量上限 |
| 聚合缓存 | 3min | `aggregator.js:24` |
| 单源缓存 | 5min | 各适配器内 |
| wash 解析缓存 | 6h | `resolver.js:18` |
| 限速 | 30 次/分钟（滑动窗口） | 只对 zreso 生效 |
| 熔断 | 连续 4 次失败 → 冷却 5min | `upstream.js:40` |

## 4. 链接跳转链路（安全性设计）

这是整个项目里工程质量最高的一段。

```
搜索结果里只有 /go/a1b2c3  ← 真实 URL 从不下发
        │
        ▼
/go/:hash  → 内存 Map 取 entry（重启即失效，刻意不持久化）
        │
        ├─ 磁力/电驴 → 不能 302，渲染可点击页面交给本地下载工具
        │
        ├─ 非 http → 拦截
        │
        ├─ resolver.isAllowedUrl(target) 白名单校验
        │     不通过 → 400「非受信任的链接」
        │
        ├─ security.assessUrl() 风险打分
        │     high  → 直接拦截页，不给继续按钮
        │     mid   → 风险页，需手动确认
        │     low   → 风险页 1 秒后自动跳（可配置为直接跳）
        │
        └─ confirm=1 → 302 真跳
```

**白名单只收叶子域名**（`resolver.js:95-146`），这条注释写得很清醒：如果收 `baidu.com`，那 `tieba.baidu.com`、`mail.baidu.com` 全部放行，等于把开放重定向开在自家门口。所以只写 `pan.baidu.com`、`pan.quark.cn`、`drive.uc.cn` 这种承载分享内容的叶子域。

已知例外：`115.com` 本身就是叶子域（`115.com/s/xxx` 就是分享页），后缀匹配会连 `passport.115.com` 一起放行，这是取舍。

## 5. 降级与稳定性：四层

| 层 | 实现 | 触发后行为 |
|---|---|---|
| TTL + LRU 缓存 | `lib/cache.js` | 命中直接返回，不打上游 |
| 滑动窗口限速 | 30 次/分钟 | 超限返回降级数据，不报错 |
| 熔断器 | 连续 4 次失败 → 停 5min | 冷却期内全走降级 |
| 本地兜底数据 | `lib/fallback.js` | 保证界面永远有东西渲染 |

设计原则写在 `aggregator.js:13`：**部分成功优于全失败**。哪怕只有一个源活着也要出结果，并把挂掉的源如实告诉前端（`providers[].ok=false` + `degraded` 数组），不装死。

另外三层进程级健壮性：

- `unhandledRejection` / `uncaughtException` 全局兜底，防止一个适配器漏 catch 让 Node 整体退出
- `EADDRINUSE` 单独处理并给**不同的退出码（2）**，避免外部重启脚本把"端口被占"当崩溃无限重试
- `POST /__shutdown` 回环地址专用停止通道 —— 因为 Windows 下 `child.kill('SIGTERM')` 底层是 `TerminateProcess`，SIGINT handler 一次都不会执行

## 6. 工程细节里 8 个可以直接复用的点

1. **单源截断**（120 条）：不做这个，一个返回 800 条的源会把其他源完全淹没，聚合就退化成单源
2. **去重键丢 query**：夸克/UC 分享链接的唯一标识在 path 里，query 全是跟踪参数，带 query 去重会重复
3. **质量分择优合并**：同一链接多源命中时，`raw_url` 存在直接 +40 分，因为"能直接打开"比"标题好看"值钱得多
4. **标题清洗的括号平衡守卫**（`aggregator.js:151-169`）：剥完尾部噪音后检查「闭括号是否多于开括号」，多于就说明切坏了左半，整条回退原文 —— 这个守卫很实用
5. **同标题折叠的防误伤**：要求标题 ≥4 字 **且** 含 ≥4 个实义字符，纯数字「2024」和泛称「资料」不折
6. **相关性权重 ×3**：早期版本只按日期排，导致"日期新但标题完全不含关键词"的条目霸屏
7. **真实 URL 不下发**：字段白名单 `PUBLIC_FIELDS` 过滤，否则 `/go` 的白名单校验等于摆设
8. **静态资源加内容哈希**（`_stamp.js`）+ 服务端 `maxAge: 0`：解决"改了代码但用户看到旧界面"

## 7. 功能清单

### 后端接口（`server.js`）

| 路由 | 作用 |
|---|---|
| `GET /api/search` | 主搜索。参数 `q`(≤80 字) / `sort`(latest\|oldest) / `cloud`(all\|quark\|baidu\|uc\|xunlei) |

| `GET /api/sources` | 已注册源与启用状态 |
| `GET /api/status` | 各源统计：命中/失败/缓存/退避/熔断 |
| `GET /api/security/check` | 单 URL 风险评估 |
| `GET /unavailable` | 降级数据专用落地页 |

| `POST /__shutdown` | 回环地址优雅退出 |

### 前端页面

`index.html`（首页）/ `search.html`（结果页）/ `404.html` / `disclaimer.html`

视觉上做了「无图设计」——不用位图，图标全用 CSS 画，减少外部依赖；另有亮暗双主题、800px 断点响应式、无滚动条、氛围层（极光/网格/噪点/暗角）、命令面板 Ctrl+K、`j/k/Enter/Esc` 键盘导航。

### jso 失效的完整证据链

1. 代码记录的目标结构：`/s/<kw>?__full=1` + 请求头 `X-Search-Full: 1` → 返回含 `<article class="result-item">` 且带 `data-real-link` 的完整 HTML（`jso.js:9-14`）
2. 实测 `GET http://j-so.com/s/教程?__full=1`（带 `X-Search-Full: 1`）：
   - 返回 **4804 字节**
   - `<title>加载中</title>`
   - `data-real-link` 出现 **0** 次
   - `result-item` 出现 **0** 次
3. 进一步看该域名的首页构建产物，其 `page-home` chunk 里的业务文案是「彩票 / 电子 / 真人 / 棋牌 / 体育 / 捕鱼 / 电竞」「等待开奖 / 封盘 / 已封盘 / 当前房间已关闭注册」

也就是说：**这个域名已经换了业务**，从网盘搜索站变成了一个博彩平台的 SPA 外壳。`jso.js` 里的正则和请求约定是针对旧版页面写的，现在必然解析为空。

代码对此是「软失败」——`parseItems` 返回空数组，`stats.parsedEmpty++`，不影响其他源。所以前端只会看到 `providers` 里 `jso: {count: 0, ok: false}`，不会报错也不会白屏。**这是设计上的正确行为，但也意味着它掩盖了「源已死」这个事实** —— 除非有人去看 `/api/status` 的 `parsedEmpty` 计数。

## 9. 合规边界与可迁移的部分

### 必须说清楚的三件事

1. **技术中性，业务不中性。** 聚合、去重、降级、白名单跳转，这些都是正当工程手段；但它们服务的对象是"未经授权传播的影视/软件/课程资源"。上游的索引本身就是侵权的，本站做的是把它做得更好用。
2. **"只是转发公开链接"不是免责理由。** 链接公开 ≠ 内容合法。国内对网盘资源索引站已有明确判例，定性方向是侵犯信息网络传播权 / 帮助侵权。
3. **上游本身不可信。** 这类站点普遍无备案、随时跑路、常被挂马。项目里写了 3 万行 `security.js` 做风险页、仿冒识别、危险文件类型标注 —— 这个投入本身就是对风险的承认。

### 架构可以原样搬到合法场景

这套「多源聚合 + 四层降级 + 白名单跳转 + 内容哈希缓存」的骨架，换个数据源就是完全正当的产品：

- **企业内部文档/知识库检索**：多个业务系统的文档索引聚合，权限白名单，跳转前确认
- **开源镜像/包索引**：聚合多个 registry，去重、版本排序、下载前风险提示
- **公开数据集搜索**：政府开放数据、科研数据集的跨站聚合
- **自家多站点的统一搜索**：把公司几个子站的搜索合成一个入口

代码几乎不用改，只需要替换 `lib/sources/*.js` 的适配器和 `ALLOWED_HOSTS`。
