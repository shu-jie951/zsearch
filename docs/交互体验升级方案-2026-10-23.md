# ZSEARCH 交互体验诊断与升级方案

> 日期：2026-10-23　范围：`public/`（4 个页面 + 5 份 CSS 4805 行 + 6 份 JS 4482 行）
> 方法：全部结论基于代码实测统计（`grep` 计数、`sed` 取片段、行号可回查），不做主观形容。
> 结论先行：**这个站的"单点设计"水准已经很高，问题几乎全部出在「体系」上** ——
> 变量定义得很克制，但使用处大量绕过变量；每个组件单独看都讲究，凑在一起就不齐。
> 所以下面 90% 的改动是"收敛"，不是"重做"。

## 1. 交互动画与过渡节奏

### 1.1 时长体系名存实亡（P0，最高优先）

**现状**

`:root` 只定义了三个时长：

```css
--dur-fast: 0.15s;  --dur-base: 0.24s;  --dur-slow: 0.42s;   /* base.css:59-61 */
```

但全站实际在用的值是 **13 种**：

| 时长 | 次数 | 出处 |
|---|---|---|
| 0.2s | 16 | 硬编码，绕开变量 |
| 0.15s | 11 | 部分用变量、部分硬编码 |
| 0.26s | 6 | 硬编码 |
| 0.32s | 5 | 抽屉/浮层 |
| 0.3s | 4 | 硬编码 |
| 0.18s | 4 | 硬编码 |
| 0.72s | 2 | 首屏 reveal |
| 880ms | 1 | 壁纸淡入 |
| 其余 0.08 / 0.24 / 0.28 / 0.4 / 0.42 | 各 1-2 | 混杂 |

**为什么"不高级"**：0.18s 与 0.2s 肉眼分辨不出，但**相邻的两个可点元素用了不同档**时，手指/鼠标划过一排按钮会感到"节奏不齐"。用户说不出哪里不对，只会觉得"这个站有点毛"。这是整体质感最常见的失分点，也是修补成本最低的一项。

**方案**：四档 + 一档专用，其余全部替换。

```css
:root {
  --dur-1: 120ms;   /* 微反馈：颜色、边框、光标 */
  --dur-2: 180ms;   /* 小元素：图标、徽章、按钮 */
  --dur-3: 240ms;   /* 基础：卡片、输入框、面板 */
  --dur-4: 360ms;   /* 大位移：抽屉、浮层进场 */
  --dur-page: 560ms;/* 仅首屏编排，见 1.6 */
}
```

替换规则：`0.08/0.15/0.18 → --dur-1`，`0.2/0.24/0.26/0.28 → --dur-2`，`0.3/0.32/0.42 → --dur-3`，`0.4/880ms → --dur-4`。

**预期效果**：全站动效只有 4 个速度档，任何两个相邻交互的"呼吸"必然同频。这是一次性改动，之后新增组件只要不写裸数字就不会漂。

### 1.2 位移与缩放三档混用（P0）

**现状**（同一站内并存）

```
home.css:304   translateY(-1px)      搜索框聚焦
home.css:862   translateY(-2px)
home.css:965   translateY(-2px)
results.css:275/627/761/1049/1081  translateY(-1px)
results.css:1119  translateY(-2px) scale(1.05)
wallpaper.css:488 translateY(-2px) scale(1.04)
home.css:451/640 / results.css:227  scale(1.06)
```

**为什么"不高级"**：抬起 1px 和 2px 表达的是同一种语义（"这个可以点"），但幅度不同就等于**同一语言里有两个词表示同一件事**。同屏出现时，视觉重量会失衡；而 `1.04 / 1.05 / 1.06 / 1.08` 四个缩放值更是典型的"每次顺手调一下"。

**方案**：三档语义，且只在需要时用。

```css
:root {
  --lift-1: -1px;    /* 行内元素：图标按钮、徽章 */
  --lift-2: -2px;    /* 块级元素：卡片、结果条 */
  --lift-press: -1px;/* 按下时反而回收，见 4.2 */
}
```

配套原则：
- **块级卡片用 `--lift-2`，行内元素用 `--lift-1`，不要交叉**；
- 缩放只保留 `1.02` 一档（悬停）与 `0.99`（按下），删掉 1.04/1.05/1.06/1.08；
- 已经在做位移的元素**不要同时改阴影档位**（见 2.4）。

**预期效果**：全站"抬起"只有一个物理含义，鼠标扫过列表时的高度变化是均匀的。

### 1.3 缓动曲线有"外来户"，弹簧曲线过冲（P0 附带）

**现状**

| 曲线 | 次数 | 问题 |
|---|---|---|
| `cubic-bezier(0.16, 1, 0.3, 1)` = `--ease-out` | 6 | ✅ 体系内，主用 |
| `cubic-bezier(0.34, 1.4, 0.64, 1)` = `--ease-spring` | 5 | ⚠️ 第二控制点 1.4 > 1，**必然过冲** |
| `cubic-bezier(0.65, 0, 0.35, 1)` = `--ease-in-out` | 2 | ✅ |
| `cubic-bezier(0.4, 0, 0.2, 1)` | 1 | ❌ Material 默认曲线，不属于本站语汇 |

**为什么"不高级"**：过冲（overshoot）是最容易被误当成"高级"的东西——它确实"活"，但在一个纸感、克制、几乎无装饰的设计里，弹一下就像在宣纸上盖了个塑料章。Material 那条曲线则是"另一个设计系统的方言"。

**方案**

```css
:root {
  --ease-out: cubic-bezier(0.16, 1, 0.3, 1);   /* 进场：快出慢收，保留 */
  --ease-in:  cubic-bezier(0.4, 0, 1, 1);      /* 新增：退出用 */
  --ease-io:  cubic-bezier(0.65, 0, 0.35, 1);  /* 位移往返 */
  --ease-spring: cubic-bezier(0.34, 1.15, 0.64, 1); /* 1.4 → 1.15，只留极轻回弹 */
}
```

- 删掉 `cubic-bezier(0.4,0,0.2,1)` 那一处，改 `--ease-out`；
- `--ease-spring` 只允许出现在"状态翻转"（勾选、开关、收藏星标），**不许用在位移/抽屉上**；
- 进场一律 `--ease-out`，退场一律 `--ease-in`——现在退场也在用 `--ease-out`，所以关闭抽屉时"起步慢、结尾急"，方向感和打开时一样，这是不符合物理直觉的。

**预期效果**：开与关的手感区分开（开：果断进入、柔和停下；关：干脆离开），这类细节是"用起来舒服但说不出为什么"的主要来源。

### 1.4 13 处 `transition: all`（P1）

**现状**：`home.css` 4 处、`results.css` 9 处。

```css
/* 典型 */
transition: all 0.2s ease;
```

**为什么是问题**：`all` 会连带过渡 `width / height / padding / inset` 这类**布局属性**——一旦某个状态变化里含布局属性，就会在主线程逐帧重排，而作者本意通常只想过渡颜色和阴影。它还会让"新增一个属性"变成"意外多出一个动画"。

**方案**：统一替换为白名单。

```css
transition:
  color var(--dur-1) var(--ease-out),
  background-color var(--dur-1) var(--ease-out),
  border-color var(--dur-1) var(--ease-out),
  box-shadow var(--dur-2) var(--ease-out),
  transform var(--dur-2) var(--ease-out);
```

**预期效果**：去掉意外过渡；交互路径上不再有隐藏的重排；新加属性不会莫名"动起来"。

### 1.5 聚焦时边框永久流光（P1）

**现状**（`home.css:373-381`）

```css
.chat-editor-content:focus-within::before {
  background-size: 34% 100%;
  animation: edge-sweep 2.8s var(--ease-in-out) infinite;  /* ← 一直跑 */
}
```

**为什么"不高级"**：用户正在**打字**的时候，输入框顶边有一道光每 2.8 秒跑一趟。这是"演示态"的动效，不是"使用态"的动效——它会把注意力从文字拉到边框上，而且循环动画在长时间停留的页面上会变成噪声。很多模板站都有这个效果，所以它同时也很"廉价"。

**方案**：只扫一次，作为"聚焦已生效"的确认信号。

```css
.chat-editor-content:focus-within::before {
  animation: edge-sweep 900ms var(--ease-out) 1;   /* 一次，不是无限 */
}
```

**预期效果**：聚焦的瞬间有一道极快的流光确认"这里活了"，然后彻底安静。功能保留，噪声消失。

### 1.6 首屏编排过长（P2）

**现状**（`base.css:343-348`）

```css
.reveal {
  animation: reveal-up 0.72s var(--ease-out) forwards;
  animation-delay: calc(var(--i, 0) * 80ms + 60ms);
}
```

按首页 5 个块算：最晚一块 60 + 4×80 = 380ms 才开始，加 720ms 动画 = **1.1s 才完全落定**。

**为什么是问题**：首屏是"第一印象窗口"。1.1s 意味着用户在 0.5s 时看到的是**半透明、正在上浮**的内容——这时如果他想点，目标还在动。参考量级：产品级入场编排通常 400–600ms 内结束。

**方案**

```css
.reveal {
  animation: reveal-up var(--dur-page) var(--ease-out) forwards;  /* 560ms */
  animation-delay: calc(var(--i, 0) * 60ms + 40ms);               /* 级联 60ms */
}
```

最晚落定：40 + 4×60 + 560 = **840ms**；若把级联层数限制在 4 层内（第 5 个及之后共用最后一档延迟），可压到 **760ms**。

**预期效果**：首屏可交互时间从 1.1s → 约 0.8s（-27%），且"上浮"的距离感不变（10px 保持）。

### 1.7 JS 与 CSS 的节奏互不知情（P2）

**现状**：JS 里与动画配合的 `setTimeout` 用了 `120 / 190 / 900 / 1500 / 1600 / 6200`，与 CSS 的 4 档时长**没有任何对应关系**。例如 CSS 说 240ms，JS 可能 190ms 就开始下一步（或 900ms 才收尾）。

**方案**：把时长集中成一份常量，JS 从 CSS 变量读，读不到再用兜底值。

```js
const dur = (name, fallback) =>
  parseFloat(getComputedStyle(document.documentElement).getPropertyValue(name)) * 1000 || fallback;

const D2 = dur('--dur-2', 180);
```

**预期效果**：以后调 CSS 一处，JS 侧的延时自动跟随，不会再出现"动画还没走完，逻辑已经进入下一步"的错位。

## 2. 视觉层级与排版细节

### 2.1 字号 15 档，0.5px 一档（P0）

**现状**（全站去重后共 15 个不同值）

```
9.5×4  10.5×16  11×14  11.5×9  12×13  12.5×10  13×6  13.5×2
14×3  14.5×1  15×2  15.5×1  16×1  18×1  21×2
```

从 9.5 到 21px，几乎每 0.5px 就有一个档位，共 **15 档**。

**为什么"不高级"**：字号的作用是**建立层级**，而层级需要"跳"。0.5px 的差异在 12px 左右的正文上不产生层级感，只产生"两行字好像一样大、又好像不太一样"的不确定感。这是排版上最典型的"精细的混乱"：数值上很讲究，感知上是噪点。

**方案**：7 档模块化阶梯，每档只承担一种角色。

| 令牌 | 值 | 用途 |
|---|---|---|
| `--fs-meta` | 11px | 来源标签、时间、徽章、页脚 |
| `--fs-caption` | 12px | 辅助说明、计数、快捷键提示 |
| `--fs-sm` | 13px | 次要正文、列表摘要 |
| `--fs-body` | 15px | 正文、输入框 |
| `--fs-card` | 18px | 结果条标题 / 卡片标题 |
| `--fs-title` | 24px | 区块标题 |
| `--fs-hero` | clamp(34px, 5vw, 46px) | 首页主标 |

迁移映射：`9.5/10.5/11 → 11`；`11.5/12/12.5 → 12`；`13/13.5 → 13`；`14/14.5/15/15.5 → 15`；`16/18 → 18`；`21 → 24`。

> 注意 `21 → 24` 是**放大**：结果页统计数字现在 21px，与 18px 的卡片标题只差 3px，层级塌陷；提到 24px 后，"统计 > 标题 > 正文"才有明确三段。

**预期效果**：任意两个相邻层级的比值 ≥ 1.15，一眼可辨；页面从"一片灰"变成"有段落感的灰"。同时 CSS 里字号声明从 15 种收敛到 7 种，后续调版不会互相打架。

### 2.2 间距没有栅格（P2）

**现状**：`padding/gap/margin` 的取值里，`5px`×11、`7px`×10、`9px`×6、`18px`×8、`14px`×7 —— 非 4 倍数共 **22 处**。

**为什么"不高级"**：留白的"高级感"来自**可预期**——眼睛会下意识寻找对齐线。5px/7px/9px 这种"手工微调"值会让元素之间出现 1-2px 的错位，单看没问题，整页扫视时会觉得"没对齐但说不上哪没对齐"。

**方案**：4px 基准，6 档。

```
--sp-1: 4px  --sp-2: 8px  --sp-3: 12px
--sp-4: 16px --sp-5: 24px --sp-6: 32px  --sp-7: 48px
```

映射：`5/6 → 4 或 8`（视上下文）、`7/9/10 → 8`、`14 → 12 或 16`、`18 → 16 或 20`。

**预期效果**：所有间距落在同一套网格上，元素左边缘、上边缘形成可被"看见"的对齐线。

---

### 2.3 z-index 是补丁，不是层级（P1）

**现状**：20 个裸值 —— `-2 -1 0 1 2 3 4 10 98 99 200 300 400 1000 1001 1040 1050 1090 1100 1150 2000`。

连号段 `1040/1050/1090/1100/1150` 是典型的"新浮层压不过旧的，就加 50"。

**为什么是问题**：这类数字**无法推理**。下次再做一个浮层，作者只能靠试；而 `1000` 这一层被 `.results-header` 自己占着（见项目记忆里的老坑：抽屉从 `<body>` 直挂也被它压住），说明层级已经发生过一次失控。

**方案**：令牌化 6 层，禁止裸值。

```css
:root {
  --z-base: 0;
  --z-sticky: 10;
  --z-header: 100;
  --z-overlay: 200;   /* 遮罩 */
  --z-drawer: 300;    /* 抽屉 / 命令面板 */
  --z-toast: 400;     /* 提示，永远最上 */
}
```

现有值映射：`-2/-1 → 保持在背景层（不用令牌）`；`0–4 → --z-base`；`10 → --z-sticky`；`98/99/200 → --z-header`；`300/400 → --z-overlay`；`1000/1001 → --z-header`；`1040–1150 → --z-drawer`；`2000 → --z-toast`。

**预期效果**：叠层关系可读（"抽屉 > 遮罩 > 顶栏 > 内容"），新增浮层时选层级而不是猜数字。

### 2.4 聚焦态阴影叠了 5 层（P1）

**现状**（首页搜索框，`home.css:296-309`）

- hover：`border-color` 变 + `box-shadow: md → lg`（3 层）
- focus：`border-color` 变 + `box-shadow: lg`（3 层）+ `::after` 的 `0 0 0 4px accent-soft`（ring）+ `0 12px 40px -12px accent-glow`（辉光）
- 默认还有 `::before` 那条 1px 内高光

即：**同一个元素在聚焦瞬间同时存在 6 个阴影/描边层**。

**为什么"不高级"**：阴影的作用是表达"离纸面多远"。多层叠加到一定数量后，边界会糊成一团浅灰，元素看起来"不干净"。真正的高级做法是**层数少、每层职责明确**。

**方案**

```css
/* 默认：细边 + 一层贴身影 */
border: 1px solid var(--border);
box-shadow: var(--shadow-sm);

/* 悬停：只加强边框，阴影不动 */
:hover { border-color: var(--border-strong); }

/* 聚焦：边框转暖 + 一圈低透明 ring，阴影保持 */
:focus-within {
  border-color: color-mix(in srgb, var(--accent) 34%, var(--border-strong));
  box-shadow: var(--shadow-sm), 0 0 0 3px var(--accent-soft);
}
```

同时**删掉 `::before` 那条内高光**（原因见 3.3）。

**预期效果**：聚焦时"边框亮起 + 一圈极淡的暖光环"，边界清晰、不发灰；阴影不再随 hover/focus 跳档，视觉重量稳定。

## 3. 配色与质感

### 3.1 同一支橙在暗色下有两个亮度（P0）

**现状**（`base.css:22-25` 与 `82-83`）

```css
/* 亮色 */
--accent: hsl(22, 76%, 52%);
--accent-soft: hsla(22, 76%, 52%, 0.1);
--accent-glow: hsla(22, 76%, 52%, 0.22);

/* 暗色：只重定义了 soft / glow */
--accent-soft: hsla(22, 76%, 58%, 0.14);
--accent-glow: hsla(22, 76%, 58%, 0.3);
```

结果：暗色下**实心橙是 52%**，而**光晕橙是 58%**——同一个品牌色出现两个明度。

**为什么是问题**：橙点是全站唯一的彩色信号（logo 的圆点、输入光标、选中态、徽章）。它在实心与光晕之间偏色时，会让人隐约觉得"这个红橙不太对"，但很难指出。而 52% 在深色底（`#0e0e11`）上其实偏闷，本该提到 56–58%。

**方案**

```css
@media (prefers-color-scheme: dark) {
  :root {
    --accent: hsl(22, 78%, 58%);                       /* 暗底提亮 */
    --accent-soft: color-mix(in srgb, var(--accent) 14%, transparent);
    --accent-glow: color-mix(in srgb, var(--accent) 30%, transparent);
  }
}
```

关键：**soft/glow 从 `var(--accent)` 派生**，不再各写一套 hsla。此后改主色，关联色自动跟随。

**预期效果**：暗色下品牌橙从"闷红"变"透亮"，且实心与光晕是同一个颜色；颜色只有一处源头。

### 3.2 `prefers-reduced-motion` 下每张卡都亮聚光（P0，真 bug）

**现状**（`polish.css:112-120`）

```css
@media (prefers-reduced-motion: reduce) {
  #resultList .result-item::before,
  .result-item.pending-in.in-view {
    animation: none;
    opacity: 1;        /* ← 问题在这 */
    transition: none;
  }
}
```

聚光层（`::before`）的圆心由 `--spot-x/--spot-y` 控制，未指向时默认 `50% 50%`。这里把 `opacity` 强制为 1，等于**每一张结果卡片的中心都有一团 7%（暗色 12%）的橙色径向渐变**。

**为什么是 bug**：聚光的设计意图写得很清楚——"只有正在被指向的那一张亮起来，整页同时亮会变成噪点"。而 reduced-motion 用户会看到**所有卡片同时亮**，整页泛橙、纸面发脏。这与"尊重系统设置"的初衷正好相反：用户关掉动效，反而得到了更重的装饰。

**方案**：reduced-motion 下聚光应该**不存在**（它是运动派生效果，不是信息）。

```css
@media (prefers-reduced-motion: reduce) {
  #resultList .result-item::before { opacity: 0 !important; transition: none; }
  .result-item.pending-in,
  .result-item.pending-in.in-view { animation: none; opacity: 1; }
}
```

**预期效果**：关动效的用户看到干净的纸面卡片，泛橙面积 100% → 0。这一行改动是本次方案里"投入产出比最高"的一项。

### 3.3 材质语言叠了 6 层，还有一件玻璃时代的遗物（P2）

**现状**：背景层有 极光（3 团漂移）+ 网格 + 噪点 + 暗角；表面层有 雾面实色 + 1px 细边 + 三层阴影 + 卡片聚光；输入框还额外有 **顶部 1px 内高光**。

**为什么是问题**

1. **内高光是玻璃时代的残留**。它的作用是模拟玻璃上缘的高光反射，但那套 `backdrop-filter` 已经在 2026-10-21 整体移除。现在它只剩一条悬在输入框顶部、两端渐隐的白线——**没有材质支撑，它就是一道莫名的线**，在浅色纸面上还容易被看成渲染瑕疵。
2. **极光 + 网格 + 噪点三者同时存在**时，背景的"信息量"偏高。三者单独看都极淡，叠起来会让纯色区域显得"不干净"，尤其在亮色主题下（纸感最需要纯净）。

**方案**

- **删除** `.chat-editor-content::before` 的内高光（`home.css:317-327`）；
- 极光保留（它是品牌氛围），**网格在亮色主题下降一半不透明度**（`--grid-opacity: 0.5 → 0.28`），暗色保持；
- 噪点保留（它是纸感的关键，且已经改为 normal 混合，不贵）。

**预期效果**：表面从"6 种材质"收到"3 种"，输入框边界变干净；亮色主题的纸面更纯，暗色主题的氛围不减。

## 4. 响应式适配

### 4.1 断点零散：800 / 767 / 720 三个挤在 80px 内（P2）

**现状**（12 个媒体查询块，用到 7 种不同条件）

```
max-width: 1100 ×2 块
max-width:  800 ×4 块
max-width:  767 ×1 块
max-width:  720 ×1 块
max-width:  640 ×2 块
min-width:  640 ×1 块
max-height: 680 ×1 块
```

`800` 与 `767` 只差 33px、功能重叠（都在收窄主栏），`720` 又夹在两者之间——典型的"每次遇到问题就加一个断点"。

**方案**：3 宽 + 1 高。

```css
@media (max-width: 1280px) { /* 桌面收窄：主栏去掉侧 padding 溢出 */ }
@media (max-width: 900px)  { /* 平板：单栏化，导航收成图标 */ }
@media (max-width: 640px)  { /* 手机：字号降一档、间距减半、触控目标放大 */ }
@media (max-height: 680px){ /* 矮屏：抽屉改为全高，去掉上下留白 */ }
```

合并规则：`1100 → 1280`（统一桌面收窄点）、`800/767/720 → 900`、`640 保留`。

**预期效果**：断点取值从 7 种减到 4 种、媒体查询块从 12 个减到 5 个左右；不会再出现"767 与 800 之间那 33px 宽的半格布局"。

### 4.2 hover 61 处 / active 9 处（P1）

**现状**

| 状态 | 数量 |
|---|---|
| `:hover` | **61** |
| `:active` | 9 |
| `:focus-visible` | 9 |
| `:focus-within` | 9 |

**为什么是问题**：反馈体系建立在 hover 上，而**触屏没有 hover**。手机上点一个结果条、一个筛选胶囊、一个图标按钮，视觉上可能**完全没有回执**——用户不确定是否点到了，会再点一次。这是移动端"不跟手"的头号原因。

**方案**：三步。

1. **所有 hover 规则包进能力查询**，避免触屏"点完一直亮着"：

```css
@media (hover: hover) and (pointer: fine) {
  .result-item:hover { … }
}
```

2. **给可点元素补按下态**（触屏唯一能感知的反馈）：

```css
.result-item:active,
.filter-chip:active,
.icon-btn:active {
  transform: scale(0.995);
  background-color: var(--surface-hover);
  transition-duration: var(--dur-1);
}
```

3. **触控目标最小 44×44**（现在 CSS 里没有任何 `min-height/min-width` 约束，实测为零）：

```css
@media (pointer: coarse) {
  .icon-btn, .filter-chip, .tag { min-height: 44px; min-width: 44px; }
}
```

**预期效果**：手机端每次点击都有明确的"按下去"回执；不会再出现误触与重复点击；符合 WCAG 2.5.5。

## 5. 整体设计一致性

### 5.1 两页搜索框有 7 处不同（P1，最有说服力的不一致）

同一个动作（聚焦搜索框），首页 `.chat-editor-content` 与结果页 `.results-ai-composer` 的表现：

| 维度 | 首页 | 结果页 | 判断 |
|---|---|---|---|
| 圆角 | `--radius-lg` 22px | `--radius-xl` 28px | ❌ 语义相同、形状不同 |
| 默认阴影 | `--shadow-md` | `--shadow-sm` | ❌ 重量不同 |
| hover 阴影 | `→ lg` | `→ md` | ❌ 提升幅度不同 |
| focus 位移 | `translateY(-1px)` | 无 | ❌ 一个有"浮起"，一个没有 |
| focus 边框 | accent **30%** 混合 | accent **42%** 混合 | ❌ 强度不同 |
| focus 光晕 | ring + 12/40px 辉光 | 仅 ring | ❌ 一个像"点亮"，一个像"描边" |
| 顶部内高光 | 有 | 无 | ❌ 一个有材质，一个没有 |

**为什么这是"最伤高级感"的一条**：用户从首页搜索，进入结果页，**同一个输入框的手感变了**。人不会说"这两个组件参数不一致"，只会觉得"这个站有点拼凑"。设计一致性不是所有东西长一样，而是**同一种交互在哪儿都一样**。

**方案**：抽出一个共享的"输入面"（surface）语义，两页都引用，只允许尺寸差异。

```css
/* 放进 base.css：输入面的唯一定义 */
.surface-input {
  background: color-mix(in srgb, var(--bg-elevated) 94%, transparent);
  border: 1px solid var(--border);
  border-radius: var(--radius-lg);
  box-shadow: var(--shadow-sm);
  transition: border-color var(--dur-2) var(--ease-out),
              box-shadow var(--dur-2) var(--ease-out);
}
.surface-input:hover { border-color: var(--border-strong); }
.surface-input:focus-within {
  border-color: color-mix(in srgb, var(--accent) 34%, var(--border-strong));
  box-shadow: var(--shadow-sm), 0 0 0 3px var(--accent-soft);
}
```

两页分别只保留尺寸差异（高度 48 vs 56、圆角按尺寸给 `--radius-lg` / `--radius-xl` 之一，但**聚焦行为完全一致**）。

**预期效果**：跨页面的同一动作手感相同；未来加第三个入口（如 404 页搜索）直接复用，不会再有第 8 处差异。

---

### 5.2 入场动画有两套节奏（P2）

- 首页首屏：`reveal-up 0.72s`，级联 80ms
- 结果列表：`lazy-in 0.44s`，逐条触发

两者都是"从下方 10px 淡入"，但速度差 0.28s。虽然是不同场景（一次性 vs 逐条），但**同一个位移语义应该共享同一个时长**。

**方案**：统一到 `--dur-page`（560ms）做首屏，`--dur-3`（240ms）做逐条（逐条本该更快，因为它要跟上滚动）。

**预期效果**：两类入场"同族不同速"，而不是"两个体系"。

---

### 5.3 关键字与变量混用（P2）

`animation: shimmer 1.4s ease-in-out infinite`（`results.css:953`）用了 CSS 关键字 `ease-in-out`，而站点定义的是 `--ease-in-out = cubic-bezier(0.65,0,0.35,1)`——**名字一样，曲线不一样**。

同类还有 `transition: color var(--dur-fast) ease`（`base.css:315`）里的裸 `ease`。

**方案**：全站禁止 `ease / ease-in-out / linear` 关键字，一律用变量。

**预期效果**：所有动效走同一组曲线，"名字对得上但实际不同"这种最隐蔽的偏差消失。

## 附：一句话总结

这个站不缺审美，缺的是**把审美变成规则**。

- 变量写了，但使用处绕过去了（时长 13 vs 3、字号 16 vs 0、间距 22 处非 4 倍）；
- 组件都做过，但没有共享定义（搜索框 7 处差异、入场两套节奏）；
- 装饰都克制，但叠起来过量（6 层材质、5 层阴影、永久流光）。

把这三件事收住，观感会从"看得出用心"变成"说不出哪里好、但就是舒服"——后者才是高级感。
