## 一、问题不是「源不够」，是「词不对」

最初的判断是"数据源覆盖不够，要多接几个源"。按这个方向查了 GitHub 上的同类项目
（`fish2018/pansou`、`lidebyte/panhub`、`zeoday/pansou_web`、`maishaninc/limitless-search`）
之后，结论反过来了：

- 我们已经在用一个**聚合上百个频道 + 18 个插件**的源（pansou）。再接一个聚合器，
  覆盖面提升有限，但会成倍增加限流风险。
- 真正让用户"搜不到"的，是**我们把用户的输入原样转发了**。

实测（同一台机器，直连上游 `so.252035.xyz`，同一天）：

| 输入 | 结果 | 耗时 |
| --- | --- | --- |
| `庆余年` | 有结果（整包很大） | 28~35s |
| `有没有庆余年的资源` | **total = 0** | 5.5s |
| `庆余年第二季` | 17 条 | 28s |
| `慶餘年` | 超时（繁体，上游标题基本是简体） | > 35s |
| `庆余年 第二季`（带空格） | 超时 | > 30s |

上游是拿关键词去和分享标题做**子串匹配**的。多打五个字的客套话，
召回直接归零 —— 而用户看到的是"这个站没有我要的东西"。

## 二、四层处理

### 1. 归一化（normalize）

- 全角 → 半角（`Ｏｆｆｉｃｅ` → `office`）
- 繁体 → 简体（231 个高频字，见 `lib/intent.js` 的 `T2S`）
- 中英文标点统一成空格
- 顺序很关键：**先转简体再做标点处理**。反过来的话「資源」这种繁体后缀剥不掉，
  因为词表里只有「资源」。

### 2. 口语剥除（stripFiller）

```
请问一下哪里能下载 沙丘2 的高清资源  →  沙丘2
有没有庆余年的资源                    →  庆余年
求三体全集资源谢谢大佬                →  三体全集
```

- **前缀**：求 / 跪求 / 请问 / 大佬们 / 谁有 / 有没有 / 帮我找 / 哪里能下载 …
- **后缀**：资源 / 链接 / 下载 / 网盘 / 高清 / 免费 / 谢谢 / 大佬 / 吗 / 呢 …
- **中缀**：`的+资源` / `之+链接`（只匹配「的/之 + 明确名词」，
  绝不能写成单个 `的` —— 那样会把「目的」「的确」一起吃掉）

**安全阀**：剥完剩不到 2 个实义字符就退回原词。`求资源`、`资源` 这类输入
宁可原样搜，也不能被吃成空字符串。

### 3. 意图识别（intent）

| 维度 | 取值 |
| --- | --- |
| 类型 | tv / movie / course / software / music / book / game / photo / general |
| 年份 | 19xx / 20xx |
| 季集 | 第二季 / S02 / Season 2 / 第12集 / 全24集 |
| 画质 | 4K / 2160p / HDR / 蓝光 / 中字 / 双语 / 国语 … |

类型不参与过滤（宁可多给，不可错杀），只用于两件事：
相关性打分时给「标题也带同类词」的结果加分；无结果时给按类型换词的建议。

### 4. 退让变体（variants）

主词没货时，按顺序再试：

1. 去季集：`庆余年第二季` → `庆余年`（整季包常常只标剧名）
2. 去年份：`考研2025年真题` → `考研 真题`（连「年」一起剥，否则剩「年真题」）
3. 去画质：`沙丘2 4K 1080p` → `沙丘2`（4K/蓝光在标题里写法极不统一）
4. 取核心词：多段查询 → 最长的中文段
5. 转简体：兜住「去修饰后才露出繁体」的情况

## 三、什么时候才放宽（成本控制）

```
主词命中数 ≥ 5   → 直接返回，不追变体
主词命中数 < 5   → 最多追 2 个变体，每个 12s 上限，串行（省上游配额）
fast=1（阶段 1） → 一律 noExpand，首屏优先
```

变体命中的条目 **降权 15%，不删除**，排在同一相关度的主命中之后。
用户要的是"能找到"，不是"只给最准的"。

三处配套：

- **缓存键用清洗后的词**：`有没有庆余年的资源` 与 `庆余年` 共享同一份聚合缓存。
- **如实交代**：响应里带 `expanded { rewritten, from, to, variants[], added }`，
  前端统计行显示一个虚线小标签「按「庆余年」检索 · 已放宽：庆余年」。
- **相关性重算**：主结果与变体结果合并后重新走一遍去重/打分/排序/折叠，
  而不是把两批结果直接拼接（拼接必然出现重复与乱序）。

## 四、相关性打分同步调整

旧规则在多词查询上有个结构性缺陷：把查询拼成一个整串去匹配
（`周杰伦 无损` → `周杰伦无损`），这个串在标题里必然不存在，
于是只能退到 2-gram 覆盖率，得分被压得很低，排在"日期新但无关"的条目后面。

新规则分两级：

| 情况 | 加分 |
| --- | --- |
| 整串命中 | +45（前缀再 +25） |
| **查询里每个词都命中（顺序无关）** | **+60** |
| 部分词命中 | +0~30 |
| 2-gram 覆盖率 | +0~15（整串或全词命中时不叠加） |

另外：多源交叉验证 +5（两个独立源都收录 → 大概率真实且没失效）；
标题只有「合集/大全/福利」又不含主词 → -8。

实测：`周杰伦 无损` 对标题「周杰伦全部专辑 FLAC 无损」从 24 分提到 64 分；
大杂烩标题「热门影视合集大全 持续更新 拿走不谢」对查询「庆余年」为 **-8 分**。

## 五、顺带做的两件事

1. **pansou 多实例轮换**（`PANSOU_BASES="https://a,https://b"`）。
   PanSou 是可自建的开源服务，限流按 IP；单实例被打到 400 时换一个往往立刻可用。
   默认单实例时行为与以前完全一致（循环只走一次）。
2. **pansou 超时 25s → 32s**（内部 20s → 28s）。实测「庆余年」要 28~35s 才吐完整包，
   25s 砍下去的结果是"明明有货却报 0 条"——这比慢更伤。阶段 1 仍压 6.5s，首屏不受影响。

## 六、验证

| 项目 | 结果 |
| --- | --- |
| `node _qa_query.js` | **36 / 36**（繁简 5、口语 10、意图 10、变体 5、相关性 6） |
| `node _qa_ui_static.js` | 55 / 55（未回归） |
| 端到端：`求三体全集的资源` | 清洗为 `三体全集` → 1 条（8.2s） |
| 端到端：`有没有庆余年的资源` | `expanded.to = "庆余年"`，改写生效；当日上游限流，结果为空 |

> 上游当天处于被限流状态（`慢源 20s 超时 + 0 条`），
> 所以端到端的"条数"不能作为最终判据；**能确认的是改写本身已经生效**
> （`expanded.to` 正确、上游收到的词是清洗后的词）。
> 等上游恢复后复跑 `_qa_ui.js` 与真实查询即可。

## 七、刻意没做的两件事

- **拼音转中文**（`qingyunian` → `庆余年`）：需要全量拼音反查表，一对多歧义大
  （`shiyan` 可以是 实验/试验/十堰）。错的代价是搜出完全无关的东西。
  上游本身能吃拼音与英文，原样透传更好。
- **同义词替换**（`苹果` → `iPhone`）：词义依赖语境，替错就是"帮我找 A，给我 B"。
  宁可让用户自己换词，也不悄悄改词。
